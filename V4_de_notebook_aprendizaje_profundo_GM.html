Qué es un tensor

Un tensor es una estructura matemática para representar datos numéricos en múltiples dimensiones. Es la unidad de datos fundamental en cualquier framework de aprendizaje profundo: toda imagen, todo texto tokenizado y todos los parámetros de una red neuronal existen en memoria como tensores.

Lo que distingue a los tensores es su rango (número de dimensiones) y su forma (shape), que indica cuantos elementos hay en cada dimensión. Conocer el rango del tensor que espera cada capa de la red es esencial para construir y depurar arquitecturas correctamente.

# CELDA — Comparación de velocidad CPU vs GPU import time import tensorflow as tf print("Verificando la disponibilidad de GPU...") print(f"TensorFlow tiene acceso a GPU: {tf.config.list_physical_devices('GPU') != []}") # Definir el tamaño de la matriz para la comparación matrix_size = 2000 # Un tamaño suficientemente grande para ver diferencias # Crear dos matrices grandes de números aleatorios A = tf.random.normal((matrix_size, matrix_size)) B = tf.random.normal((matrix_size, matrix_size)) print(f"\nRealizando multiplicación de matrices ({matrix_size}x{matrix_size}) en CPU y GPU...") # --- Ejecución en CPU --- start_time_cpu = time.time() with tf.device('/CPU:0'): # Forzar la ejecución en CPU C_cpu = tf.matmul(A, B) end_time_cpu = time.time() time_cpu = end_time_cpu - start_time_cpu print(f" Tiempo de ejecución en CPU: {time_cpu:.4f} segúndos") # --- Ejecución en GPU (si está disponible) --- if tf.config.list_physical_devices('GPU'): start_time_gpu = time.time() with tf.device('/GPU:0'): # Forzar la ejecución en GPU C_gpu = tf.matmul(A, B) end_time_gpu = time.time() time_gpu = end_time_gpu - start_time_gpu print(f" Tiempo de ejecución en GPU: {time_gpu:.4f} segúndos") print(f" La GPU es {time_cpu / time_gpu:.2f} veces más rápida que la CPU para esta operación.") else: print(" GPU no disponible para comparación de tiempos.")

Por qué importa entender los tensores en la práctica

Un tensor es la forma en que una red neuronal recibe y transforma los datos. En visión computacional, una imagen no entra al modelo como una fotografía, sino como una matriz de números; un conjunto de imágenes entra como un tensor de mayor rango. Por eso es importante reconocer la forma de los datos: cantidad de imágenes, alto, ancho y canales. Si una capa espera una entrada con cierta forma y recibe otra, el modelo no puede continuar.


También importa usar la librería y el hardware adecuados. En Aprendizaje Profundo se repiten millones de operaciones sobre tensores grandes, como multiplicaciones de matrices a muchos pixeles e imágenes por lote. La comparación anterior muestra la idea central: una CPU puede resolver la operación, pero una GPU está diseñada para ejecutar muchas operaciones numéricas en paralelo. Por eso, TensorFlow o PyTorch con soporte de GPU permiten entrenar y probar modelos mucho más rápido cuando el volumen de datos crece.

El dataset MNIST

MNIST (Modified National Institute of Standards and Technology) contiene 70,000 imágenes en escala de grises de 28x28 píxeles de dígitos escritos a mano del 0 al 9, divididas en 60,000 para entrenamiento y 10,000 para prueba. Es el punto de partida ideal para el análisis exploratorio de datos de imagen porque su estructura es clara y esta perfectamente balanceado.

De tensores abstractos a datos reales

La sección anterior explicó que un tensor organiza datos por dimensiones. Ahora usamos esa idea con un dataset real: al cargar MNIST obtenemos arreglos con miles de imágenes y etiquetas; después los convertimos a tensores para que TensorFlow pueda operar sobre ellos durante el entrenamiento. En visión computacional, revisar el shape permite confirmar cuántas imágenes hay, cuál es su resolución y cuántos canales tiene cada muestra.

EDA visual: de inspeccionar datos a tomar decisiones de modelado
Antes de entrenar, cada visualización debe responder una pregunta práctica. Si el EDA no cambia ninguna decisión del flujo, entonces falta conectar el hallazgo con el preprocesamiento, la arquitectura o la evaluación.
Carga y shape
¿Qué entra al modelo?
Confirma número de muestras, resolución, canales y etiquetas. Define si se requiere resize, conversión RGB o cambio de formato.
Rango de pixel
¿Cómo escalar los datos?
Determina si basta normalizar a 0-1 o si conviene estandarizar con media y desviación. Esto afecta la estabilidad del entrenamiento.
Balance visual
¿Hay clases subrepresentadas?
Permite decidir si se necesitan pesos por clase, más datos, sobremuestreo o aumentos selectivos para clases con pocos ejemplos.
Similitud entre clases
¿Qué errores esperar?
Anticipa confusiones como 4-9, 5-8 o 7-9. Después se contrasta con la matriz de confusión del modelo.
Atípicos y ruido
¿Qué muestras revisar?
Identifica trazos débiles, ejemplos ambiguos y posibles etiquetas incorrectas antes de culpar a la arquitectura.
En un dataset propio, este mapa funciona como checklist: cada hallazgo del EDA debe terminar en una decisión concreta sobre datos, modelo o evaluación.

Qué es un modelo preentrenado

Un modelo preentrenado es una arquitectura cuyos pesos fueron optimizados sobre un dataset masivo y están disponibles para descargarse y reutilizarse. Al incorporar esos pesos en un proyecto nuevo se aprovecha el conocimiento capturado como: texturas visuales, relaciones semánticas, reglas gramaticales, etc, sin necesitar los datos originales ni el costo computacional del entrenamiento.

Este enfoque, denominado transfer learning, es la estrategia más eficiente para prototipado rápido, especialmente cuando el dataset propio es pequeño o el presupuesto computacional es limitado.

La idea importante del ejercicio es que un modelo preentrenado no es una solución automática: es un punto de partida. Su utilidad depende de tres decisiones: qué tan parecido es el nuevo dataset al dataset de preentrenamiento, si se usa como extractor de características o con fine-tuning, y si el preprocesamiento respeta exactamente la entrada que el modelo espera.

Flujo para datos de imagen

Este flujo cubre las decisiones específicas para datos de imagen. A diferencia del texto, las imágenes son tensores numéricos que ya tienen valores continuos, pero requieren transformaciones geométricas y de intensidad para ser compatibles con el modelo preentrenado que se quiere usar.

Características relevantes a documentar en este flujo:

  • Formato del tensor: forma esperada por el modelo: (H, W, C) donde C es el número de canales (1 para escala de grises, 3 para RGB).
  • Normalización de pixel: rango de valores que espera el modelo: [0, 1], [-1, 1] o valores de media y desviación de ImageNet.
  • Redimensionamiento: interpolacion usada al cambiar el tamaño de la imagen (bilineal, bicubica).
  • Conversión de canales: si el dataset es escala de grises y el modelo espera RGB, se debe replicar el canal.
  • Desajuste de dominio: la diferencia entre el dominio de preentrenamiento (ImageNet) y el propio determina si se necesita fine-tuning y de que tipo.

Interpretación: ¿Por qué falla sin fine-tuning?

El modelo entrenado en ImageNet (fotografías naturales a color) no generaliza a dígitos manuscritos en escala de grises redimensionados. Sin fine-tuning, accuracy ≈ 12%, muy cerca del azar para 10 clases. El resultado no significa que el código esté mal: significa que el modelo no tiene una cabeza ni representaciones finales adaptadas al dominio evaluado.

  • Dominio diferente: ImageNet contiene fotos naturales a color; MNIST tiene dígitos manuscritos en escala de grises.
  • Distribución de características: Los filtros aprendidos en las primeras capas (bordes, texturas) son genéricos, pero las capas finales esperan características de objetos complejos.
  • Estrategia correcta: primero entrenar una cabeza nueva con el backbone congelado; después descongelar capas superiores con learning rate bajo.
Decision didactica: MNIST o CIFAR-10 para fine-tuning

MNIST es ideal para demostrar el fallo porque el cambio de dominio es extremo. Para enseñar fine-tuning correctamente conviene pasar a CIFAR-10: sigue siendo pequeño y accesible, mantiene 10 clases, pero usa imágenes RGB de objetos reales. Eso lo hace más cercano a ImageNet y permite observar una mejora razonable al adaptar un backbone preentrenado.

De MobileNetV2 a ResNet18: Fine-tuning por fases

En la sección anterior se exploró MobileNetV2 sin fine-tuning para observar el desajuste de dominio. Ahora se aplica la estrategia completa de fine-tuning por fases usando ResNet18 sobre CIFAR-10. La diferencia clave: en lugar de dejar el backbone congelado para siempre, se entrena en dos etapas distintas.

Estrategia de fine-tuning por fases

Fase 0 — Baseline

Evaluar qué ocurre sin adaptar pesos al dataset nuevo. Sirve para separar problemas de preprocesamiento de problemas de aprendizaje.

Fase 1 — Solo cabeza

Congelar el backbone y entrenar únicamente la capa final adaptada a las 10 clases de CIFAR-10.

Fase 2 — Ajuste fino

Descongelar las capas superiores del backbone con learning rate bajo para adaptar rasgos de alto nivel.

Por que ResNet18 y no MobileNetV2 aqui

ResNet18 introduce las conexiones residuales (skip connections), que permiten entrenar redes profundas sin que el gradiente desaparezca. MobileNetV2 está optimizado para velocidad en dispositivos móviles; ResNet18 es la arquitectura de referencia para entender cómo funciona el fine-tuning en redes con bloques residuales. Ambos usan pesos de ImageNet, pero sus arquitecturas internas, y como responden al fine-tuning, son distintas.

Por que aqui cambiamos a CIFAR-10

Fine-tuning no solo consiste en ejecutar mas épocas: consiste en adaptar pesos preentrenados a un dominio compatible. CIFAR-10 conserva el reto de 10 clases, pero usa objetos RGB, por lo que el aprendizaje transferido desde ImageNet tiene una base visual más razonable que en MNIST.

Este ejemplo usa PyTorch en lugar de TensorFlow, lo que permite comparar el mismo concepto de transfer learning en dos frameworks distintos y entender que el patrón de fine-tuning es independiente del framework.

Para la práctica se usa un subconjunto de 200 imágenes de entrenamiento y 200 de prueba, lo que permite ejecutar el experimento en minutos.

Se aplican RandomHorizontalFlip y ColorJitter solo al conjunto de entrenamiento. Al conjunto de prueba solo se le aplica resize y normalización. Mezclar augmentation en test es un error común que infla artificialmente la varianza del resultado y dificulta la comparación entre experimentos.

Detección de Objetos con YOLOv8 IMAGEN
md
▶

De clasificar a detectar: una tarea más compleja

La clasificación asigna una etiqueta a toda la imagen. La detección de objetos va más allá: localiza y clasifica múltiples objetos dentro de la misma imagen, devolviendo por cada uno sus coordenadas (bounding box), la clase predicha y la confianza del modelo.

Tarea Salida del modelo Ejemplo de uso
Clasificación 1 etiqueta por imagen "Esta imagen es un gato"
Detección N cajas + N etiquetas + N confianzas "Hay 2 personas y 1 auto en posiciones X,Y"
Segmentación 1 etiqueta por pixel "Estos píxeles son carretera, estos son peaton"

Cómo funciona YOLO

YOLO (You Only Look Once) divide la imagen en una cuadrícula y en una sola pasada predice, para cada celda, las cajas delimitadoras y las probabilidades de clase. Esto lo hace extremadamente rápido y adecuado para aplicaciones en tiempo real. YOLOv8, la versión actual, mejora la arquitectura con un backbone CSPDarknet más eficiente y una cabeza de detección desacoplada.

Non-Maximum Suppression (NMS)

YOLO puede generar múltiples cajas para el mismo objeto. El postprocesamiento aplica NMS para eliminar cajas redundantes y conservar solo la de mayor confianza por objeto. Si el modelo detecta 12 cajas y NMS elimina 4 redundantes, el resultado final son 8 detecciones.

El nivel más granular: etiqueta por pixel

La segmentación semántica lleva la visión computacional a su máxima precisión: en lugar de una etiqueta por imagen (clasificación) o por objeto (detección), asigna una etiqueta a cada pixel de la imagen. Si una imagen tiene 640×480 píxeles, la salida del modelo es una máscara de 307,200 valores, cada uno indicando la clase del pixel correspondiente.

Aplicaciones donde la forma importa

En diagnóstico médico, segmentar un tumor requiere conocer su contorno exacto, no solo si existe en la imagen. En conducción autónoma, distinguir carretera de acera pixel a pixel es crítico para la navegación. En inspección industrial, delimitar una grieta con precisión es distinto a solo detectarla.

DeepLabV3 Convoluciones atrous + ASPP Múltiples escalas, escenas complejas Escenas urbanas, conducción autónoma
Mask R-CNN Faster R-CNN + rama de máscara Segmentación de instancias individuales Objetos solapados, industria

Objetivo del flujo NLP: de frases propias a un modelo publicable

En este bloque trabajamos un ciclo completo de aprendizaje profundo aplicado a texto desde la definición del problema hasta el guardado y despliegue básico para recibir frases reales.

El ejemplo usa clasificación multiclase de sentimiento porque permite distinguir frases negativas, neutrales y positivas; el mismo flujo puede adaptarse a intención de usuario, urgencia de tickets, tema de comentarios, riesgo de abandono, clasificación de correos o cualquier tarea donde una frase tenga una etiqueta.

Clase: flujo principal

Problema, recolección de datos, EDA, tokenización, baseline, fine-tuning y evaluación.

Producto mínimo

Más datos, IMDB, descongelamiento gradual, Hugging Face Hub, Spaces, SageMaker, Vertex AI o Azure ML.

Actividad guiada: definición del problema de texto

La actividad consiste en elegir una tarea que pueda resolverse con frases cortas. Debe quedar claro qué representa cada frase, cuáles serán las etiquetas, de dónde saldrán los ejemplos y qué decisión tomaría una persona o sistema con la predicción del modelo.

md
▶

Por qué usamos BERT y DistilBERT en este flujo

Para una práctica de NLP necesitamos un modelo que permita explicar el flujo completo sin entrenar una arquitectura desde cero. BERT es una buena referencia porque introdujo una forma muy efectiva de representar texto con contexto bidireccional: cada palabra o subpalabra se interpreta considerando lo que aparece antes y después en la frase. Esto lo vuelve útil para clasificación, búsqueda semántica, extracción de entidades, preguntas y respuestas, y muchas otras tareas de lenguaje.

Elegimos DistilBERT porque conserva la lógica central de BERT, pero con menos capas y menor costo computacional: carga más rápido, consume menos memoria, permite experimentar en Colab o equipos personales y mantiene los mismos conceptos clave que se deben entender antes de hacer fine-tuning.

Tip: modelo pequeño primero

En un proyecto real conviene iniciar con un modelo base ligero para validar datos, etiquetas, métricas y pipeline. Después, si el problema lo justifica, se compara contra modelos más grandes como BERT, RoBERTa, DeBERTa o modelos especializados en español.

md
▶

Por qué el texto necesita un tratamiento distinto al de las imágenes

Una imagen ya es una matriz numérica: sus píxeles tienen valores entre 0 y 255 y solo necesitan normalización y redimensionamiento para entrar al modelo. El texto, en cambio, es una secuencia de caracteres que no tiene representación numérica natural. Antes de pasarlo a la red neuronal es necesario convertirlo en enteros mediante un proceso llamado tokenización.

Además, los textos tienen longitudes variables. Una frase puede tener 5 palabras y un párrafo 200. Las redes neuronales esperan tensores de forma fija, lo que obliga a establecer una longitud máxima y rellenar las secuencias cortas con un token especial de padding.

Tip: no empieces entrenando

En NLP conviene revisar primero si las etiquetas son claras, si hay frases ambigüas y si el modelo base ya resuelve parte del problema. Fine-tuning debe ser una decisión posterior al baseline, no el primer paso.

md
▶

Conceptos clave del preprocesamiento en NLP

Tokenización. El texto se divide en unidades llamadas tokens. El tokenizador es un algoritmo que realiza esta división. En DistilBERT, primero se intenta mantener palabras completas y, si una palabra no esta en el vocabulario, la divide en subtokens. Por ejemplo, excelente se convierte en excel + ##ente. Se usa el prefijo ## para indicar continuación. Esto permite cubrir cualquier vocabulario con solo 30,522 entradas fijas.

Vocabulario de BERT. El vocabulario no es una lista de palabras completas como un diccionario tradicional; es una tabla fija que asigna un ID numérico a cada token. Incluye tokens especiales como [CLS], [SEP], [PAD] y [UNK]; palabras frecuentes como the, product o good; signos de puntuación; números; y fragmentos de palabra como ##ing, ##mente o ##ción. Cuando una palabra no existe completa, el tokenizador busca la combinación de subtokens más útil dentro de ese vocabulario.

La forma práctica de imaginarlo es como una tabla de dos columnas: token e id. Por ejemplo, [PAD] → 0, [CLS] → 101, [SEP] → 102. Después de tokenizar, el modelo no recibe texto, sino una secuencia de IDs como [101, 2023, 2003, 2307, 102]. Por eso el tokenizador y el modelo deben venir del mismo checkpoint: si se mezclan vocabularios, los IDs dejan de representar los tokens esperados.

Tokens especiales. El modelo BERT y sus derivados requieren dos tokens que no vienen del texto original. El token [CLS] se inserta al inicio de cada secuencia y su representación final es la que se usa para clasificación. El token [SEP] marca el fin de la secuencia. Omitirlos produce resultados incorrectos sin ningún mensaje de error.

Padding y attention mask. Cuando se procesa un batch de frases de distinta longitud, todas se rellenan hasta la longitud de la más larga con el token [PAD]. Para que el modelo ignore esas posiciones de relleno, se genera un vector binario llamado attention_mask: valor 1 en cada posicion real y valor 0 en cada posición de padding.

Logits en lugar de probabilidades. Muchos modelos de texto no devuelven probabilidades directamente, sino logits: puntajes crudos sin normalizar. Un logit más alto indica que el modelo considera esa salida más compatible con el contexto, pero todavía no es una probabilidad. Para convertir logits en probabilidades se aplica softmax; después se elige la clase o token con mayor probabilidad mediante argmax.

La forma de los logits depende de la tarea. En clasificación multiclase de sentimiento, la salida puede tener 3 valores: uno para NEGATIVO, otro para NEUTRAL y otro para POSITIVO. En un modelo de lenguaje enmascarado, como BERT prediciendo [MASK], la salida para esa posición tiene un valor por cada token del vocabulario: aproximadamente 30,522 puntajes. El token con logit más alto es la predicción más probable antes de aplicar softmax.

En imagen el preprocesamiento es geométrico y de intensidad: cambiar el tamaño de la imagen, convertir canales y normalizar valores de pixel a un rango numérico. Todo esto opera sobre datos que ya son matrices de números.

En NLP el preprocesamiento es lingüístico: dividir texto en tokens, mapear cada token a un entero del vocabulario, insertar tokens especiales de protocolo, rellenar hasta longitud fija y generar la máscara de atención. WordPiece: el algoritmo de tokenización de BERT

WordPiece es un algoritmo de tokenización subpalabra (subword tokenization). En lugar de dividir el texto en palabras completas, lo divide en fragmentos más pequeños llamados tokens. Esto es crucial para manejar:

  • Palabras desconocidas: Si la palabra completa no está en el vocabulario, se divide en subpalabras conocidas.
  • Flexiones y derivaciones: "running" se tokeniza como ["run", "##ning"], permitiendo al modelo generalizar sobre variaciones.
  • Palabras raras: En lugar de usar un token genérico [UNK], conserva información semántica parcial.

Sensibilidad a mayúsculas y variantes del modelo: BERT y DistilBERT tienen versiones cased y uncased. En una versión uncased, el tokenizador convierte el texto a minúsculas antes de buscar tokens, por lo que Apple y apple tienden a representarse igual. En una versión cased, las mayúsculas se conservan, lo cual puede ser importante para nombres propios, siglas, entidades o textos donde la capitalización aporta significado.

Las versiones originales como bert-base-uncased o distilbert-base-uncased fueron entrenadas principalmente en inglés, con un vocabulario optimizado para ese idioma. Para ejercicios con español u otros idiomas conviene usar variantes multilingües, como bert-base-multilingual-cased o distilbert-base-multilingual-cased/uncased, porque su vocabulario contiene fragmentos útiles para muchos idiomas. La decisión cased vs uncased debe registrarse como parte del preprocesamiento, ya que cambia la tokenización y puede afectar las métricas.

⚠️ Error común: Ignorar la tokenización

Un principiante podría pensar: "Si uso el tokenizador de BERT, los tokens se alinean perfectamente con el texto original". Esto es falso. En "unhappily", el tokenizador genera ['un', '##happy', '##ly'], no se puede mapear directo 1:1 con caracteres.

Esto causa problemas cuando:

  • Intentas extraer relevancia por palabra (importance of each word): los índices no coinciden.
  • Necesitas mapear predicciones a palabras originales: requiere deshacerse la tokenización.

Solución: Mantener registro de word_ids() del tokenizador, que mapea cada token a su palabra original.

Lectura del baseline

El resultado del baseline no debe interpretarse como evaluación final. Por ejemplo, POSITIVE | confianza: 0.72 significa que, entre las etiquetas disponibles del modelo, POSITIVE obtuvo la probabilidad mayor con 72%.

Ese valor no debe leerse como garantía de verdad. Un modelo puede estar muy confiado y equivocarse si el idioma, el dominio o las etiquetas no coinciden con el problema. En frases ambigüas o mixtas, una confianza intermedia es una señal útil para revisar ejemplos, ajustar etiquetas o definir un umbral mínimo antes de usar la predicción en una aplicación real.

Por qué hacer fine-tuning y cuándo

Un modelo preentrenado como DistilBERT fue optimizado para predecir tokens enmascarados en Wikipedia y BooksCorpus. El fine-tuning ajusta los pesos del modelo a la distribución de los datos propios, lo que generalmente produce una mejora sustancial respecto al modelo base sin ajuste.

La regla práctica es: si el dominio del dataset propio es similar al de preentrenamiento, el fine-tuning de pocas épocas suele ser suficiente. Si el dominio es especializado (textos médicos, legales, código fuente), puede ser necesario pre-ajustar sobre un corpus del dominio antes de hacer fine-tuning de la tarea.

Las 3 estrategias de fine-tuning en NLP

  • Congelamiento parcial: se congelan todas las capas Transformer y se entrena solo la cabeza de clasificación. Rápido, ideal para datasets muy pequeños (<1,000 muestras) o cuando el dominio es idéntico al preentrenamiento.
  • Descongelamiento gradual: se entrena primero la cabeza, luego se descongelan capas Transformer de arriba hacia abajo en etapas sucesivas, reduciendo la tasa de aprendizaje en cada etapa. Útil cuando el dominio es algo diferente.
  • Fine-tuning completo con LR diferencial: se entrenan todas las capas con tasas de aprendizaje distintas por capa: más baja en capas iniciales (representaciones generales), más alta en capas superiores y en la cabeza. Técnica conocida como discriminative learning rates.

Etapa 3: Preprocesamiento de texto

Antes de tokenizar, revisamos si conviene limpiar el texto. En modelos tradicionales era común convertir a minúsculas, quitar acentos y remover puntuación. En Transformers multilingües, esa decisión debe evaluarse: acentos, signos de exclamación, emojis y mayúsculas pueden aportar información útil.

  • Texto original: se conserva para auditoría y para comparar resultados.
  • Limpieza mínima: normaliza espacios y saltos de línea sin destruir señales lingüísticas.
  • Emojis: pueden eliminarse, conservarse o convertirse en tokens textuales como emoji_positivo; la decisión depende del problema.
  • Decisión inicial: conservar acentos, puntuación y emojis; crear una variante adicional para analizar el efecto de convertir emojis.

La limpieza de texto cambia el dataset. Conviene registrar si se quitaron acentos, emojis, signos o mayúsculas, porque esa decisión puede cambiar la tokenización y las métricas.

Etapa 6: Fine-tuning con el Trainer de Hugging Face

La clase Trainer automatiza el loop de entrenamiento: forward pass, cálculo de pérdida, backpropagation, actualización de pesos. Configuramos:

  • num_train_epochs=3: Pasar 3 veces por el dataset (pequeño, así que es rápido)
  • per_device_train_batch_size=2: Procesar 2 ejemplos por iteración (bajo debido al dataset pequeño)
  • learning_rate=5e-5: Tasa de aprendizaje conservadora para preservar el conocimiento preentrenado
  • weight_decay=0.01: Regularización L2 para evitar overfitting en dataset pequeño
  • eval_dataset: conjunto separado para medir generalización durante el flujo

Decisión del ejercicio: con pocas frases se muestra el mecanismo de entrenamiento multiclase. El resultado debe interpretarse como demostración del pipeline, no como modelo listo para producción.

Lectura de las métricas de ejemplo

Estas métricas muestran cómo interpretar el desempeño del modelo en el conjunto de prueba. Como el dataset es muy pequeño, los números no deben leerse como rendimiento final, sino como una guía para entender qué revisar cuando se entrena con más datos.

  • Accuracy test = 0.60: el modelo acertó 3 de 5 ejemplos de prueba. Es una métrica fácil de leer, pero puede ocultar problemas si una clase domina el dataset.
  • F1 macro = 0.52: resume el equilibrio entre precisión y recall dando el mismo peso a NEGATIVO, NEUTRAL y POSITIVO. Es útil para detectar si alguna clase queda débil.
  • Precision: de las veces que el modelo predijo una clase, indica cuántas fueron correctas. Por ejemplo, POSITIVO con precision 1.00 significa que las predicciones positivas realizadas fueron correctas.
  • Recall: de los ejemplos reales de una clase, indica cuántos logró recuperar. POSITIVO con recall 0.50 significa que solo recuperó la mitad de los positivos del test.
  • Support: indica cuántos ejemplos reales de cada clase hay en el test. Aquí hay 1 NEGATIVO, 2 NEUTRAL y 2 POSITIVO; con tan pocos casos, un error cambia mucho las métricas.

Una extensión adecuada es repetir el flujo con más frases por clase, revisar una matriz de confusión y comparar si el f1_macro mejora de forma estable entre distintas particiones train/test.

Etapa 7: Testing e inferencia con frases nuevas

Después de entrenar, necesitamos una función de inferencia reutilizable. Esta función recibe una frase nueva, aplica el mismo tokenizador, ejecuta el modelo, convierte logits a probabilidades y devuelve una respuesta legible. Esta es la unidad mínima que después se publica en una API.

No pruebes solo frases fáciles. Incluye frases mixtas como "funciona bien, pero llegó tarde" para observar si el modelo es demasiado confiado o si necesita más ejemplos de entrenamiento.

Descongelamiento gradual de capas (Layer Unfreezing)

DistilBERT tiene 6 capas Transformer + 1 capa de embeddings + 1 cabeza de clasificación. La estrategia de descongelamiento es:

  1. Congelamiento inicial: Solo entrena la cabeza de clasificación (última capa)
  2. Descongelamiento gradual: Descongela capas Transformer de arriba hacia abajo (últimas primero)
  3. Learning rates diferenciales: Capas inferiores (representaciones genéricas) aprenden lentamente; capas superiores (específicas de tarea) aprenden más rápido

¿Por qué funciona?

  • Capas inferiores aprendieron patrones genéricos (palabras, sintaxis) que siguen siendo útiles en IMDB
  • Capas superiores contienen representaciones específicas de SST-2 (críticas cortas) que pueden no transferir bien a IMDB (reseñas largas)
  • Descongelar gradualmente permite que el modelo se adapte sin borrar el conocimiento preentrenado

Visualización de la arquitectura:

DistilBERT:
  ├─ Embeddings (CONGELADO en etapa 1, DESCONGELADO en etapa 3)
  ├─ Transformer Layer 0 (más genérica)
  ├─ Transformer Layer 1
  ├─ Transformer Layer 2
  ├─ Transformer Layer 3
  ├─ Transformer Layer 4
  └─ Transformer Layer 5 (más específica de tarea, CONGELADA en etapa 1; DESCONGELADA desde etapa 2)
  └─ Classification Head (DESCONGELADA siempre)

En la primera etapa, congelamos todas las capas Transformer y solo entrenamos la cabeza de clasificación. Esto es rápido y seguro: adaptamos solo la capa de decisión final a IMDB, manteniendo las representaciones de DistilBERT.

Decisiones:

  • num_train_epochs=2 (pocas épocas, datos ya son muchos)
  • per_device_train_batch_size=16 (dataset más grande permite batch mayor)
  • learning_rate=2e-4 (más alto porque solo la cabeza aprende)

Etapa 2: Descongelamiento parcial — Últimas 2 capas Transformer

En la Etapa 1, la cabeza aprendió a clasificar IMDB. Ahora desbloqueamos las últimas 2 capas Transformer (capas 4 y 5), que son las más cercanas a la cabeza y contienen representaciones específicas de la tarea.

Estrategia de learning rates:

  • Capas congeladas: learning_rate = 0 (no entrenan)
  • Capas 4-5 descongeladas: learning_rate = 1e-4 (más lento que la cabeza)
  • Cabeza de clasificación: learning_rate = 2e-4 (más rápido, ya está adaptada)

En Hugging Face, esto se implementa creando grupos de parámetros en el optimizador y pasándolos al Trainer.

Etapa 3: Descongelamiento total con learning rates diferenciales (DLR)

En la etapa final, desbloqueamos todas las capas pero con tasas de aprendizaje diferentes:

  • Capas 0-2 (genéricas): learning_rate = 5e-5 (más lento, preservar conocimiento)
  • Capas 3-5 (específicas): learning_rate = 1e-4 (medio)
  • Embeddings + cabeza: embeddings con learning_rate bajo y cabeza con learning_rate mayor

Esta técnica se conoce como Discriminative Learning Rates (DLR) y es especialmente efectiva cuando los dominios son bastante diferentes.

Qué es TensorFlow Hub

TensorFlow Hub es un repositorio abierto mantenido por Google que centraliza modelos preentrenados y componentes reutilizables para tareas de aprendizaje profundo. A diferencia de descargar pesos de una fuente arbitraria, TF Hub provee modelos versionados con documentación estandarizada, lo que facilita la reproducibilidad y el mantenimiento.

Los modelos disponibles abarcan clasificación de imágenes, detección de objetos, segmentación, embeddings de texto, análisis de audio y modelos generativos. Cada módulo puede descargarse con una sola línea de código e integrarse directamente como una capa de Keras mediante hub.KerasLayer.

Cómo funciona la integración con Keras

La clase hub.KerasLayer envuelve cualquier módulo de TF Hub como si fuera una capa nativa de Keras. Esto significa que puede insertarse dentro de un tf.keras.Sequential o en la API funcional de Keras sin cambiar el resto de la arquitectura. El parámetro trainable=False congela los pesos del módulo durante el entrenamiento (extractor puro), mientras que trainable=True los descongela para fine-tuning.

Ventaja principal de TF Hub

Con pocas líneas de código se accede a modelos que requirieron semanas de entrenamiento y millones de imágenes. El flujo típico es: cargar el feature extractor congelado, agregar una cabeza densa personalizada, entrenar solo la cabeza con LR alta, y opcionalmente descongelar el extractor para fine-tuning con LR baja.

Tipos de módulos disponibles en TF Hub

  • Feature vectors: extractores sin cabeza que producen un vector de representación. Ej: MobileNetV2 feature vector de 1,280 dimensiones.
  • Classification: modelos completos con cabeza de clasificacion para ImageNet. Útiles para comparar sin fine-tuning.
  • Text embeddings: modelos que convierten texto en vectores de representación semántica. Ej: Universal Sentence Encoder.
  • Object detection: modelos para detección de múltiples objetos con bounding boxes. Ej: EfficientDet, SSD MobileNet.

Documentar cada decisión desde la primera celda — dataset, modelo, preprocesamiento, semilla, versiones — es lo que convierte un experimento en ciencia reproducible y un prototipo en base solida para el siguiente paso.

Ejercicio 1 — EDA con otro dataset de imagen

La actividad consiste en reemplazar MNIST por el dataset Fashion-MNIST (disponible en tf.keras.datasets.fashion_mnist). Repite el analisis completo: balance de clases, imagen promedio, varianza intra-clase, mapa de densidad y correlacion entre clases. Ejercicio 2 — Visualizar el espacio de embeddings

Usa el extractor de características de MobileNetV2 (sin la cabeza de clasificacion) para obtener vectores de 1,280 dimensiones de 500 imágenes de MNIST (50 por clase). Investiga: las clases se separan bien en el espacio de representacion de ImageNet? ¿Qué pares quedan solapados?

Ejercicio 3 — Analisis de tokens en NLP

La actividad consiste en tomar 10 frases de diferente longitud (de 5 a 80 palabras) y analizar como el tokenizador de DistilBERT las procesa. La tabla debe incluir: número de palabras originales, número de tokens WordPiece, razon de expansion (tokens/palabras), y cuáles palabras se dividieron en subtokens. ¿Qué patrón observas en las palabras que se subdividen? ¿Qué implicación tiene esto para el diseño del dataset?

Ejercicio 4 — Fine-tuning de MobileNetV2 sobre MNIST

La actividad consiste en adaptar el pipeline de imagen para hacer fine-tuning real de MobileNetV2 sobre los 10 dígitos de MNIST. Se debe: (a) agregar una cabeza densa de 10 clases, (b) entrenar solo la cabeza durante 5 épocas, (c) descongelar el extractor y reentrenar con LR=1e-5 durante 3 épocas adicionales, (d) evaluar con F1 macro y matriz de confusión, (e) comparar la accuracy con un modelo equivalente entrenado desde cero sobre MNIST. Los hiperparámetros y resultados deben registrarse en un JSON.

Ejercicio 5 — Comparar 3 modelos en el mismo dataset IMDB

Repite el fine-tuning sobre IMDB con tres modelos distintos de Hugging Face: distilbert-base-uncased, bert-base-uncased y roberta-base. Usa exactamente los mismos hiperparámetros y el mismo split del dataset para los tres. Se comparan accuracy, F1 macro, tiempo de entrenamiento por época y tamaño del modelo en disco. Los tres experimentos se registran en JSONs separados. ¿Qué modelo ofrece la mejor relación precisión/costo?

Ejercicio 6 — Implementar descongelamiento gradual en NLP

La actividad consiste en implementar la estrategia de descongelamiento gradual para DistilBERT sobre IMDB: (a) entrena solo la cabeza durante 2 épocas con LR=2e-3, (b) descongela las dos últimas capas Transformer y entrena 2 épocas adicionales con LR=5e-5, (c) descongela todas las capas y entrena 2 épocas con LR=2e-5. Se registra la accuracy de validación al final de cada fase y se compara con las estrategias 1 y 2 del notebook.

Ejercicio 7 — Dataset propio con etiquetas personalizadas

La actividad consiste en construir un dataset de texto propio de al menos 300 muestras sobre un tema de interés (reseñas de productos, comentarios de redes sociales, titulares de noticias) con una clasificación de 3 clases. Etiqueta las muestras manualmente en un CSV. Carga el dataset con datasets.Dataset.from_csv, tokeniza, divide en train/val/test y realiza fine-tuning completo de DistilBERT. Se compara la accuracy con el pipeline zero-shot de facebook/bart-large-mnli sobre las mismas muestras. ¿Qué estrategia es más práctica para el caso de uso?

Ejercicio 8 — Curvas de aprendizaje y diagnóstico de sobreajuste

Para el fine-tuning completo de DistilBERT sobre IMDB, genera curvas de pérdida y accuracy tanto para entrenamiento como para validación a lo largo de las épocas. Identifica el punto de sobreajuste (si existe). Se implementan dos técnicas de regularización: (a) aumento del weight_decay a 0.1, y (b) early stopping con paciencia de 2 épocas. Se comparan las curvas resultantes y se documenta cuál técnica produjo el mejor modelo según el criterio de F1 en validación.

Ejercicio 9 — Reproducibilidad total con MLflow

La actividad consiste en integrar MLflow al pipeline de fine-tuning de NLP para registrar automáticamente todos los hiperparámetros, métricas por época y artefactos del modelo. Ejecuta el mismo experimento dos veces con semillas distintas (42 y 123) y registra ambas corridas. Usa la interfaz web de MLflow para comparar los resultados. ¿Qué tanto varían las métricas entre semillas? ¿Qué indica esta varianza sobre la estabilidad del entrenamiento?

Ejercicio 10 — Pipeline de inferencia en producción

La actividad consiste en tomar el mejor modelo fine-tuned guardado con save_pretrained y construir una función de inferencia robusta que: (a) acepte texto en español o inglés, (b) preprocese y tokenice correctamente, (c) retorne la etiqueta predicha junto con la confianza y el tiempo de inferencia, (d) maneje casos extremos como texto vacío o texto de más de 512 tokens. Se documenta la función con ejemplos de uso y se registra el contrato de entrada/salida en el JSON del experimento.

Para todos los ejercicios — criterios de entrega
  • Cada ejercicio debe entregarse como un notebook independiente con celdas Markdown documentando cada decisión tomada.
  • Todos los experimentos deben incluir un JSON de configuración con los parámetros usados y los resultados obtenidos.
  • Las figuras deben guardarse en results/figures/ con nombres que incluyan el número de ejercicio y la fecha.
  • El repositorio Git debe tener al menos un commit por ejercicio con un mensaje descriptivo del tipo ejercicio-N: descripción breve.
  • Los ejercicios de nivel avanzado (7-10) deben incluir una celda final de reflexión donde se explique qué se aprendió, qué fue sorprendente y qué haría diferente en una segunda iteración.
